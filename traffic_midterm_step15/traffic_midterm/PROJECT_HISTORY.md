# 車禍責任主張分析專案：期中開發過程與最終交付紀錄

本紀錄整理截至第十五步可由程式、對話及匯出檔案確認的過程，供組員理解系統、重現實驗與自行撰寫期中報告。依使用者要求不製作 PDF，也不將本文件當成已排版完成的繳交報告。

## 一、目前做成了什麼

這是一個免費本機執行的研究原型。使用者輸入事故描述，系統整理案件欄位和待查主張，檢索法規與相似裁判摘要，辨識提供的證據能支持哪些主張，最後以中立調解模板整理結果。

核心研究問題是：如何區分「某個駕駛行為有沒有發生」「這個行為是否造成事故」以及「當事人應負什麼責任」，避免把一項指控或違規直接推成全責。

期中已完成的範圍包括本機網頁、可編輯輸入、混合式主張擷取、BM25 檢索、結構化證據規則、Ollama 串接、三組模型比較、原始輸出保存、雙人初始標註與結果分析。

目前調解功能是依標籤產生的固定模板，並非多角色自由對話。系統未讀取真實影片，未鑑定警方文件，不會自動判定責任比例、賠償金額或調解條件。此處是在說明實作邊界，不是法律意見。

## 二、專案最初如何形成

原先題目是結合 RAG、Claim Verification、責任分析與調解模擬。設計上希望先從事故描述找出主張，再用法規、裁判與本案證據檢查主張，最後輔助使用者理解自己論述的強弱。

早期實作選擇 Python 標準函式庫、本機 HTTP 介面與免費本機模型，降低額外套件、雲端 API 與部署成本。檢索採用 BM25，而非需要向量模型與向量資料庫的方案。這是目前基線的實作選擇，沒有把尚未做出的語意檢索寫成已完成。

早期文件的工程檢查為 54 項測試、離線規則示範與初版來源庫。當時真實模型比較尚未完成；那些文件的時間點與現在不同。原始第 1–7 步的全部對話並未完整出現在目前可核對紀錄中，因此本節依程式與早期文件重建功能建置過程，不虛構每個步驟當時的精確名稱或操作順序。

### 初期建立的資料

- 法規庫：12 筆摘要，涉及 9 個不同條文。
- 裁判庫：10 筆相似裁判摘要。
- 開發案例：5 件、5 項主張。
- 測試案例：10 件、15 項主張。
- 事故與本案證據為合成研究資料，不是真實當事人提供的事故卷宗。
- 法規與裁判記錄保留來源網址、查閱日及摘要類型。摘要不是完整原文，也沒有法律專家複核。

原始案例與 silver labels 為 AI 編寫。後來人工標註沒有改變合成案例的來源性質，也不會使資料自動成為真實事故資料。

### 初期建立的表示方式

主張使用 JSON 記錄：`id`、`text`、`subject`、`kind`、`predicate`、`polarity`，以及必要時的 `derived_from`。

`subject` 指主張針對誰，`speaker` 指誰提出說法。兩者不同，例如「B 說 A 超速」的被指控者是 A，提出者是 B。

`kind` 分為事實、因果、責任及其他／無關；`predicate` 是可供比對的行為或結論代碼，例如 `speeding`、`cause:lane_change`、`liability:100`。`polarity` 記錄肯定或否定。

證據另有 `id`、`source_type`、`description`、`reviewed` 與 `assertions`。`reviewed` 僅代表使用者核對轉錄；不表示軟體已獨立驗證原始檔案。

## 三、第八步：接上真正的本機模型

早期說明以 Qwen3 為模型規劃；第八步更新將網頁、CLI 與 HTTP 介面的預設模型統一為 `qwen2.5:3b-instruct`。這是後續實際實驗使用的模型，不能把舊文件中的 Qwen3 名稱沿用到本次結果。

Qwen2.5 請求不傳 `think` 參數。模型輸出使用 JSON schema，temperature=0、seed=42、num_ctx=8192、num_predict=3072。程式只連線到本機 Ollama；沒有在錯誤時改用付費雲端服務，也不會自行下載模型。

### 串接中發生的問題

模型曾回傳不符合預期的主張 ID／輸出結構。step8b 強化檢查，要求每個輸入主張都完整回傳、不重複、不新增主張，並保留原始請求與回應。部分模型回覆截斷、無效 JSON 或缺少 ID 時，會記錄為失敗，不當成有效分類。

真正本機案例成功後，確認的是連線、輸出格式、主張對應與原始紀錄都有完成。當時模型仍把超速事實與全責推論混在一起；因此第八步完成只代表串接通過，沒有聲稱準確率通過。當時對話記錄的 step8b 自動測試數為 71。

## 四、第九步：補上擷取、原文引用與推論鏈

第九步加入「預覽模型擷取」及「採用這份主張」流程。使用者可以先核對擷取結果，再決定是否送入分析。

每項原文主張附上 `source_quote`，程式檢查引用文字確實出現在事故描述。這只確認引用來源，不能證明事故敘述是真的。

若原文把一個行為直接連到責任結論，系統會加上因果待查問題。例如「A 無照，所以 A 全責」會新增「A 無照是否與事故發生有因果關係？」。新增項目標為 `generated_check_question`，不是使用者原本提出的事實，也不能算成成功擷取到的原文主張。

同時修正調解模板的主張對應，避免把事實主張的錯誤說成全責推論。修改輸入後，介面會清除舊分析，以免將舊結果誤認成新輸入的答案。第九步更新記錄為 98 項自動測試通過。

## 五、第十步：真實模型擷取失敗與逐次修正

### 使用的開發描述

> 我騎機車直行，對方開汽車左轉。對方說我無照，所以我應負全部責任。我有行車紀錄器。

這段描述在多次開發中重複使用，因此後來不能稱為未接觸的獨立測試。

### 最初失敗

模型把「直行、左轉」填到道路類型，把「無照」填到車種，漏掉無照指控，也把全責主張的類型與正反方向填錯。程式依欄位與原文引用檢查攔下結果，並保存失敗原始輸出。

### step10a：把擷取任務拆小

案件欄位和主張拆成較單純的任務，車種、動作、道路類型限制各自詞彙，事實、因果與責任分開處理。軟體測試增至 111 項。

但實機模型仍會讓全責主張引用錯句子，交換提出者與被指控者，並把全責接到錯誤的行為前提。這顯示通過模擬／單元測試不等於真實模型會正確理解句子。

### step10b：限制引用候選與補強角色提示

責任主張只能選含責任文字的原文片段，並強化角色提示。測試增至 116 項，但真實模型仍把不同主張的文字、predicate 和前提拼在一起。僅調整提示並沒有充分解決問題。

### step10c：改成混合式擷取

不再讓小模型自由生成全部主張。程式從原文辨識受限的行為與責任候選，固定可確認的引用、類型與前提；模型主要擷取案件欄位，必要時對未知角色做受限核對。複雜句型、不明角色或無法辨識的內容留待人工處理。

這是「規則＋模型」的混合方法，不是純 LLM 擷取效果。保守規則也可能漏掉詞彙範圍之外的主張，因此不能說已支援任意中文事故敘述。該更新記錄為 134 項自動測試通過。

同一案例的主要擷取結果之後正確：A 為機車直行、B 為汽車左轉；B 指控 A 無照；A 全責的說法連到無照指控，另補因果待查問題；提到行車紀錄器不等於影片已被分析。

### step10d：修正問題文字與引用診斷

因果問題原先文字不精確，後來改成「A 無照是否與事故發生有因果關係？」而不是檢查「對方說我無照」這句話本身是否造成事故。

引用錯誤也開始區分「ID 不存在」與「既有法規／裁判被誤放為本案證據」。此時診斷文字修正不應被冒稱為模型原始答案改善。測試數為 141。

### 角色互換案例

> 我開汽車直行，對方騎機車左轉。我說對方超速，所以對方應負全部責任。我有行車紀錄器，但尚未提供影片內容。

此案例確認 A 是指控者、B 是被指控超速者，並產生「B 超速是否與事故發生有因果關係？」。完整分析沒有把未提供的影片當成已核對本案證據，但模型仍有分類及引用欄位錯誤。

### step10e：最終判定改由規則產生

提供已核對 E1、內容僅支持 B 超速時，原先規則判支持，最終輸出卻仍保留模型的證據不足。同時，引用欄位錯誤會把原本的過度推論改成證據不足。

為處理這些問題，step10e 將最終標籤改為採用 `verify_claim` 的結果；模型原始答案另存為 `raw_model_result`，引用錯誤另列警告。

這不只是小幅文字修正，而是實質方法變更：對固定主張與結構化證據，Verification 的最終標籤不再依模型原始標籤或 RAG 資料決定。規則會直接依核對狀態、主體、predicate、polarity 等欄位運算。這個版本的自動測試數為 144。

修正動機是處理已觀察到的不一致，而不是把測試答案寫死在程式中；規則不是依 T01、T02 等案例 ID 查表。但是，規則與合成案例／標註定義接近，仍限制了滿分的研究說服力，不能由「沒有按案例 ID 寫答案」推論沒有過度適配風險。

### 證據狀態對照測試

| 輸入條件 | C1：B 超速 | C2：超速造成事故 | C3：因此 B 全責 |
| --- | --- | --- | --- |
| 無可用證據 | 證據不足 | 證據不足 | 過度推論 |
| 已核對 E1，僅支持超速 | 支持 | 證據不足 | 過度推論 |
| E1 改為未核對 | 證據不足 | 證據不足 | 過度推論 |
| 已核對 E1，記載未超速 | 證據不足並記錄反向證據 | 證據不足 | 過度推論 |

這些測試驗證程式在指定輸入下的處理方式，不代表一般化法律判斷已經正確。

### step10f：調解模板補上反向證據

先前 JSON 已記錄反向證據，調解文字卻只泛稱「還需補證據」。step10f 補成明確提醒「已有與此主張相反的證據（E1）」或存在衝突。這是模板修正，不需再呼叫模型。測試增至 149 項。

第十步依開發案例測試的範圍完成；當時仍有模型錯誤、檢索相關性不足和語意評估未完成等限制。

## 六、第十一步：先跑開發組批次流程

使用 5 個開發案例、5 項固定主張，依序執行 LLM Only、LLM＋RAG、LLM＋RAG＋Verification。三組都沒有執行失敗。

| 組別 | 正確／主張數 | Accuracy |
| --- | --- | --- |
| LLM Only | 3／5 | 60% |
| LLM＋RAG | 1／5 | 20% |
| Verification 最終 | 5／5 | 100% |

這次仍是對 AI silver labels 的開發組試跑。逐項分析發現，加入 RAG 後模型會把本案證據與相似裁判混淆，也會把事實、因果與責任層級混在一起。Verification 原始模型只對 1／5，另外四項由規則修正。

相關原始檔保留於 `results/step11_dev_pilot/`。這組數字不和後續測試組合併計算。

## 七、第十二步：雙人初始標註、分歧與最終採用

為便於兩位組員一次完成工作，建立四張工作表：填寫說明、主張標註、來源相關性、來源摘要。表中未放入 AI 預選分類答案，也沒有要求每個標籤都必須使用。

原始標註含組員一與組員二各自的標籤、理由與證據 ID；來源相關性另填各自選擇的法規／裁判 ID 與理由。

### 五種標籤的操作定義

| 標籤 | 本次定義 |
| --- | --- |
| 支持 | 可採用的本案證據直接支持完整主張 |
| 部分支持 | 同一主張可分成幾個部分，證據明確支持其中一部分 |
| 證據不足 | 缺乏可用證據、未核對，或有反向／衝突證據未解決 |
| 過度推論 | 結論超出前提，例如單由無照或酒駕直接推出全責 |
| 無關 | 該主張與事故爭點缺少關聯 |

原始五分類沒有 Refuted，故反向證據仍列證據不足並保留 conflict／反向 ID。這會把不同情況放進同類，必須在理由中區分。單純「沒有因果證據」的因果主張，與「由個別行為直接斷定全責」的責任跳躍也依本次既定標註規則分開處理。

### 評估程式同步修正

step12 新增參考檔載入與版本檢查，核對案例 ID、主張 ID、來源 ID、案例與來源庫雜湊。metadata 不再把這份標註一律寫成人工 gold，而是記錄真實的輔助整理來源。

## 八、第十三步：三組真實模型比較

本機使用者執行以下指令，回傳 `summary.json` 與 `runs.json`：

```cmd
python main.py evaluate --backend ollama --model qwen2.5:3b-instruct --split test --gold data/reference_annotations.json --output results/step13_comparison
```

使用同一模型、固定資料、相同主張、相同證據；RAG 與 Verification 使用相同的檢索結果。LLM Only／RAG 每案一次請求，Verification 每項主張一次，三組共 35 次模型呼叫。

| 組別 | 正確／主張數 | Accuracy | 四類 Macro-F1 | 固定五類 Macro-F1 |
| --- | --- | --- | --- | --- |
| LLM Only | 5／15 | 33.3% | 0.350 | 0.280 |
| LLM＋RAG | 7／15 | 46.7% | 0.500 | 0.400 |
| Verification 最終 | 15／15 | 100% | 1.000 | 0.800 |

每組 10 案均成功，共 30 案次、45 項分類。參考標籤分布為支持 4、證據不足 6、過度推論 4、無關 1，沒有部分支持。

四類 Macro-F1 只平均有樣本的四類；固定五類指標將沒有樣本的類別 F1 記為 0。不能將兩種定義混用，也不能說五類皆已經測試成功。

模型為 qwen2.5:3b-instruct，量化 Q4_K_M，digest 為 `357c53fb659c5076de1d65ccb0b397446227b71a42be9d1603d46168015c9e4b`。使用者回傳環境為 Windows、Python 3.11.9、Ollama 0.40.6。CPU／GPU、記憶體與實際運算裝置未在匯出檔記錄，不自行補寫。

## 九、第十四步：核對結果與分析錯誤

重新依逐項輸出計算 Accuracy、兩種 Macro-F1、各類 precision／recall／F1、P@3 與 R@3，均與 summary 相符；也核對案例、來源與參考檔雜湊。

RAG 對 T06－C1、T06－C2、T09－C2 有改善，對 T10－C1 退步，因此淨增加兩項正確。Verification 原始模型對 9／15，六項經規則修正後變成 15／15。

| 項目 | 模型原始標籤 | 規則後標籤 |
| --- | --- | --- |
| T02－C1：B 無照 | 證據不足 | 支持 |

## 十、第十五步：最後檢查與事後純規則基線

本步不再調整分類規則、提示、案例、參考標籤或重新執行 LLM 比較。使用既有 `--backend offline`，搭配同一份已採用參考檔，補算純規則基線。

```cmd
python main.py evaluate --backend offline --split test --gold data/reference_annotations.json --output results/step15_rules_baseline
```

純規則的 15 項最終標籤與先前三組實驗中的 Verification 最終標籤完全相同，均為 15／15。這是第十五步事後補算的診斷基線，不偽裝成原本已預先規劃的第四組模型實驗。

這個結果具體說明：目前 Verification 最終分類可完全由規則重現，三組結果不足以證明 LLM 或 RAG 對最終標籤有額外貢獻。LLM 仍參與擷取與原始分類、提供可分析的模型輸出，但尚未證明它改善最終分類相較純規則的成績。

交付包對程式重新執行自動測試，並檢查封包後的版本可載入資料、重現規則基線及核對已保存結果。驗證結果另存於 `records/verification_receipt.json` 與 `records/final_unit_tests.txt`。

## 十一、目前程式怎麼連起來

| 檔案 | 工作內容 |
| --- | --- |
| main.py | serve、demo、check-model、extract、evaluate、review-metrics 的 CLI 入口 |
| traffic/core.py | 輸入驗證、保守拆解、BM25、證據規則、離線分析與調解模板 |
| traffic/claim_candidates.py | 原文受限候選與角色、否定、責任關係處理 |
| traffic/extraction.py | 案件欄位模型擷取、原文引用檢查、混合擷取、因果待查問題 |
| traffic/llm.py | Ollama 請求、模型輸出格式、三組分類、原始答案與引用診斷 |
| traffic/pipeline.py | 需要時先擷取，再用固定主張進行分類 |
| traffic/server.py | 本機 HTTP 路由與失敗原始輸出保存 |
| static/index.html | 輸入、擷取預覽、採用主張、分析、來源與 JSON 匯出介面 |
| traffic/evaluate.py | 參考標註載入、分類與檢索指標、逐案保存、人工輸出審查格式 |
| tests/ | 核心、HTTP、模擬模型、引用、擷取、角色、證據界線及評估測試 |

### 實際工作流程

1. 使用者輸入事故描述。
2. 若沒有固定主張，混合擷取建立案件及主張預覽，必要時要求人工處理。
3. 使用者確認／採用主張後，固定主張送入分析。
4. RAG 模式檢索最多三筆法規與三筆裁判摘要。
5. 模型生成標籤、理由及引用 ID。
6. 程式驗證格式及 ID，保存原始結果。
7. Verification 模式依本案結構化證據規則產生最終標籤，另留原始模型答案與引用警告。
8. 調解模板依最終標籤與衝突狀態產生文字，不推算責任比例。

### BM25 的細節

用中文字元與相鄰字元 bigram，並保留英文詞及數字作為索引詞。k1=1.5、b=0.75，法規與裁判分開檢索，每類最多三筆。沒有關鍵字重疊時可回傳空結果，並不是一定要塞滿三筆。這裡沒有向量 embedding 或向量資料庫。

### 重要邊界

- A／B 不代表一定誰有責任，只是固定當事人代號。
- 來源引用在原文出現，不代表該說法是真的。
- 已核對轉錄是輸入條件，不是程式完成了證據鑑定。
- 事實成立不會自動支持事故因果，因果成立也不等於全責。
- 相似裁判不是本案法院認定。
- 模型輸出失敗應保留失敗數及回應，不能只挑成功或高分案例。
- UI 擷取流程與固定主張分類實驗不同，不能把後者的分數當作端到端擷取分數。

## 十二、重現與展示指令

所有指令都在含 `main.py` 的資料夾執行。Windows 使用 `python`；其他系統可依安裝情況改為 `python3`。

### 開啟本機網頁

```cmd
python main.py serve
```

瀏覽器開啟 `http://127.0.0.1:8765`。若改程式後頁面仍舊，重新啟動服務並按 Ctrl+F5。重新整理可能讓輸入回到預設，需要重新填寫；目前未承諾表單自動持久化。

### 檢查既有本機模型

```cmd
python main.py check-model --model qwen2.5:3b-instruct
```

需要新機安裝模型時才執行 `ollama pull qwen2.5:3b-instruct`，模型下載不包含在交付包內。不要把已有模型的電腦無謂重裝，也不要混用不同模型比較三組。

### 重新執行工程測試

```cmd
python -m unittest discover -s tests
```

這些測試含模擬 Ollama，不能拿測試通過率當模型準確率。

### 檢查保存結果

```cmd
python tools/verify_saved_results.py
```

此指令只核對檔案及已保存結果，不呼叫模型。原始三組結果已保存，沒有必要為了交付再跑一次。

### 如需重新跑比較

```cmd
python main.py evaluate --backend ollama --model qwen2.5:3b-instruct --split test --gold data/reference_annotations.json --output results/reproduction_new_run
```

新執行請使用不同輸出資料夾，保留原始三組比較。temperature=0 與固定 seed 不保證跨硬體／版本逐字完全一致。

### 純規則基線重現

```cmd
python main.py evaluate --backend offline --split test --gold data/reference_annotations.json --output results/rules_reproduction_new_run
```

不需要 Ollama。

## 十三、可以向老師清楚說明的內容

本專案完成可執行原型，並對同一模型、同一組固定主張做了三組探索性比較。模型常混淆事實、因果與責任層級；結構化規則能在目前案例中修正部分錯誤。純規則診斷顯示目前最終分類不需要模型即可重現，故不主張已證明 LLM 的額外推理貢獻。

如果被問「為什麼改規則」，可以說明實際錯誤與修改：已支持的事實被忽略，以及引用錯誤覆蓋主張判定。再明確交代選擇的修法使最終分類改由規則決定。不能只用「修 bug」迴避方法已改變的事實。

如果被問「為什麼 100%」，應指出受限結構化輸入、小型合成案例、與開發重疊、規則和標註定義相近，以及純規則同樣滿分。這樣回答比把它描述成通用法律判斷準確率更符合證據。

如果被問「模型還做了什麼」，可以指出混合擷取中的案件欄位／必要角色核對，以及三組原始分類與理由生成。但目前沒有正式量測端到端擷取 F1，也沒有證明模型提升最終標籤相較規則的成績。

如果被問「調解是否完成」，目前是規則狀態驅動的中立模板，多角色、多輪自由對話仍未完成。
